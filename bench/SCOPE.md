# Benchmark v1: scope

Pheasa's benchmark v1 measures how well language models handle skills that exist only in
Khmer: encoding variants, number words and dates, register vocabulary, spelling and word
segmentation. Its items are written natively, not translated from English, and every
answer is scored after `pheasa.normalize`. The decision to cut v1 to five tasks is D-017.

## How it relates to existing benchmarks

Khmer already appears in multilingual evaluations. SEA-HELM's
[datasets page](https://github.com/aisingapore/SEA-HELM/blob/main/docs/datasets_and_prompts.md)
(commit `cc8e95a`, checked 2026-11-23) lists Khmer in:

- SEA-NLI, marked "Native", CC BY-SA 4.0;
- SEA-IFEval, marked "Human translation", CC-BY-4.0;
- SEA MT-Bench, marked "Human Translation", CC BY-NC-SA 4.0.

The SEA-HELM README also lists a Khmer MCQA set (20 Jan 2026) whose origin is not
documented. Belebele, SIB-200, FLORES and NTREX cover Khmer through translation.

So Pheasa does **not** claim to be the first Khmer-native LLM benchmark. The claim is
narrower: **the first benchmark of Khmer-specific skills (encoding, word segmentation,
register, spelling, number words), written natively and scored after Pheasa
normalization.** Docs, the dataset card and the paper use this wording.

## What v1 includes

| Task | How items are made | Scorer | Items | Why it is in v1 |
|---|---|---|---|---|
| `encoding-equivalence` | Generated from Khmer text with `pheasa.normalize`, then human-verified | `choice` | ~200 | Only Pheasa can generate and check these at scale; a direct test of Khmer encoding |
| `numbers-and-dates` | Generated by rule (CLDR Khmer number and date data), then human-verified | `exact` | ~200 | Exact answers, cheap to make, common in real documents |
| `register-vocabulary` | Hand-written | `choice` | 100–150 | Royal, monastic and common vocabulary is cultural knowledge that translated sets miss |
| `spelling-correction` | Correct sentences with one common misspelling inserted | `exact` | 100–150 | Basic written-Khmer skill; normalization keeps encoding noise out of the score |
| `word-segmentation` | Hand-segmented sentences | `boundary_f1` | 100–150 | Every Khmer pipeline segments, and no shared test set exists |

**Deferred to v2** (specs stay in `tasks/`, marked deferred):

- `reading-comprehension`: expensive to write well, and overlaps Belebele and SEA-NLI.
- `translation-en-km`, `translation-km-en`: FLORES and NTREX already cover translation,
  and new references need licensed source text.

## Splits

Each task's items are split once, when they are promoted, and never reshuffled:

| Split | Share | File | Where it lives |
|---|---|---|---|
| dev | ~20% | `items/<task>/dev.jsonl` | Public repo and dataset. For prompt development and few-shot examples. |
| public test | ~50% | `items/<task>/test.jsonl` | Public repo and gated dataset. Carries the canary. |
| held-out test | ~30% | `items/<task>/heldout.jsonl` | Never in the public repo (git-ignored). Kept privately; scored only for the leaderboard. Carries the canary. |

- Assignment is stratified by item type (for example "same" and "different" pairs, or
  number and date items) so each split has the same mix.
- An item enters any file under `items/` only with `verified_by` and `verified_at`.
  `scripts/validate_items.py` enforces this, the canary in test and held-out files, and
  the file names above.
- Test and held-out items never appear in prompts sent to other models, few-shot
  examples, docs, commit messages or issues.
- Drafts live in `drafts/<task>/`, which is local-only. Only the maintainer promotes
  drafts, and drafts are never scored as results.

## Reviewer protocol

1. **Primary verification.** The maintainer (a native speaker) checks every item and
   either fixes, drops or approves it. Approved items get `verified_by` (annotator ID)
   and `verified_at`.
2. **Second review.** Two or three additional native-speaker reviewers each re-check
   about 20% of each task's items, sampled at random within each split and item type.
   Reviewers work independently and do not see each other's answers:
   - for `choice` tasks, the reviewer answers the item without seeing the reference,
     then marks whether the item is valid (one clearly correct answer);
   - for `exact` tasks, the reviewer writes their own answer and marks whether the
     reference is correct and whether other answers should also be accepted;
   - for `word-segmentation`, the reviewer segments the sentence independently.
3. **Agreement.** Reported per task, before any adjudication: Cohen's κ for two
   reviewers, Krippendorff's α for more, on the answer and on the valid/invalid
   judgment; boundary F1 between annotators for segmentation.
4. **Adjudication.** Disagreements go back to the maintainer. An item is fixed, given
   extra accepted answers, or dropped; the change is logged with the item.
5. **Guidelines.** Each task has written annotation guidelines in English (Khmer
   version finalized by the maintainer), including the segmentation convention and the
   register standard used.

Reviewers are identified by pseudonymous IDs in item files.

## Models

Planned systems, with exact versions fixed when the budget is approved: GPT (OpenAI),
Claude (Anthropic), Gemini (Google), Llama (Meta), Qwen (Alibaba), Gemma (Google),
SEA-LION (AI Singapore) and SeaLLM (DAMO Academy). Every run uses `pheasa bench` with a
`--dry-run` estimate first and a `--max-usd` limit, and caches every raw response.

## Analysis

- Per task and model: mean score with 95% bootstrap confidence intervals, in English
  and Khmer prompts, with a note wherever intervals overlap.
- **Headline: what normalization changes.** For tasks scored by exact match
  (`numbers-and-dates`, `spelling-correction`) and segmentation, count the model answers
  that are wrong under plain exact match (raw strings) but correct after
  `pheasa.normalize`, per model. This measures how much existing Khmer evaluations
  misjudge models because of invisible encoding differences, and only a benchmark built
  on a Khmer normalizer can report it. The harness needs a raw-string scorer alongside
  the normalized one for this.
- Error analysis per item type (for example attested vs constructed encoding variants,
  digits vs words vs dates).

## Release targets

- **Dataset:** a gated Hugging Face dataset under `pheasaKhmer` (D-004) with the dev and
  public test splits, the canary and a dataset card. Items derived from Wikipedia text
  carry CC BY-SA 4.0; other items CC BY 4.0 (D-001).
- **Leaderboard:** scores on the public and held-out test sets, regenerated from cached
  results.
- **Paper:** an arXiv write-up of the tasks, the reviewer agreement and the
  normalization finding.

## Open decisions (for the maintainer)

1. **API budget** for the eight model families (a `--dry-run` estimate comes first).
2. **Reviewers:** who the two or three extra native reviewers are, and how they are paid.
3. **Khmer maths word problems:** whether to add a sixth task. Any question the
   maintainer wrote for YMO needs YMO's permission first.
4. **Leaderboard location:** a static page in this repo's site, or a Hugging Face Space
   under `pheasaKhmer`.
5. **Held-out storage:** where `heldout.jsonl` files are kept (a private Hugging Face
   dataset under `pheasaKhmer` is the default proposal).
